The web renders somewhere else. Only pixels reach the user.

Glass Fence intercepts a user's HTTPS request and answers it with a live video stream instead of a web page. The real browsing happens inside a single-use container that is destroyed the moment the user disconnects. Nothing executable ever reaches the endpoint. The containment layers around that container, and which of them are switched on in this deployment, are set out precisely in section 07.

01 — Overview

What the product does

Traditional web filtering makes a binary choice: allow a site and accept its code, or block it and break the user's work. Isolation removes the choice. The site is allowed to run — just not anywhere that matters.

Interception, not installation

The user points their browser's proxy at Glass Fence. TLS is terminated with an enterprise CA, so the platform sees the request in the clear and decides per host whether to isolate. No agent, no plugin, no extension on the endpoint.

One session, one destination

Each isolated request gets its own freshly created container, pinned by managed browser policy to a single allowed host. There is no shared browser, no shared profile and no shared cache between users.

Destroyed, not cleaned

Sessions are not sanitised and reused — the container is deleted. Anything a site dropped on disk, in storage or in memory goes with it. The next visit starts from the image, byte-identical.

The security boundary is a process and network boundary, not a parser. It does not depend on recognising malicious content — which is why it holds against content that no signature or heuristic has seen before.
02 — Session lifecycle

What happens between the click and the pixels

Five stages. The first four complete before the user sees anything; the fifth is what makes the model defensible.

1 · Intercept

Request arrives at the proxy. TLS is terminated with the enterprise CA, so policy can act on the real URL rather than an opaque tunnel.

2 · Decide

The host is matched against the isolation list. Non-isolated traffic is filtered and forwarded normally — isolation is selective, not all-or-nothing.

3 · Launch

A container is created, pinned to that one host, and reports healthy in about ten seconds. Sessions for the same host are reused while active.

4 · Stream

The user's original tab is answered with a viewer that plays the container's screen and sound. The address bar still shows the real site.

5 · Destroy

On disconnect the container is removed with --rm. An idle reaper collects anything left unattended.

03 — Streaming architecture

How a screen becomes a stream

The pixel path is a GStreamer pipeline feeding a WebRTC sender. Every stage is chosen for time-to-photon rather than file-size efficiency — this is an interactive desktop, not a video on demand.

Three decisions that define the feel

  • Capture only what changed. The encoder is driven by X damage events, so a static page costs almost no CPU. Measured idle draw is under a fifth of one core.
  • Never encode a stale frame. The queue is one frame deep and drops the old one rather than the new one. Under load the picture degrades; it does not fall behind.
  • Keep keyframes frequent. A viewer cannot decode anything until its first keyframe, so the 2-second interval is a correctness requirement, not a bandwidth setting.

Quality is a deliberate trade, and it is tunable

Bitrate, resolution, frame rate, encoder speed and the quantiser floor are all runtime settings — no rebuild. On a constrained network the same session can be re-pointed toward responsiveness or toward sharpness in about forty seconds.

04 — Audio architecture

Sound, in both directions

Audio is a separate encoded track, not part of the video. The container has no sound hardware, so the platform gives it virtual devices — which is also what lets the user's microphone appear inside the isolated browser.

Two settings in this path are correctness issues, not tuning knobs. A lossy queue anywhere on the audio path discards samples, and the receiver then accelerates playback to catch up to the clock — audible as sound cutting out and replaying fast. Discontinuous transmission produces the same artefact on quiet passages. Both are disabled. Video may drop frames; audio may not.
05 — Camera architecture

Giving an isolated browser a webcam

A microphone can be synthesised entirely in userspace. A camera cannot — Chromium enumerates video devices through the kernel, so the platform has to present a real device node that is fed from the network.

A loopback node cannot be shared, and getting this wrong costs you 97% of your frame rate. Every session was originally handed the same device. A v4l2loopback node has one frame slot and a shallow buffer, so concurrent writers interleave and each reader sees a fraction of the frames — measured at 1 fps in the isolated browser while the device itself advertised 30. Sessions now claim a distinct node and release it on teardown, and the camera runs at the full 30 fps. The reservation is also self-healing: a container removed out-of-band would otherwise strand its node and silently leave every later session without a camera.

The consequence for capacity planning is simple and easy to miss: the number of loopback nodes provisioned on the host is the number of simultaneous camera users. This host runs four. It is a one-line kernel-module setting, it is not persistent across reboot, and it must be sized deliberately rather than left at the default of one.

Why camera latency is structural

The user's own face is not composited locally. It travels to the container, is decoded, drawn into the virtual display, re-encoded as part of the screen, and sent back. That is a full network round trip plus an extra decode and encode — so camera self-view will always lag more than the rest of the picture. Reducing the camera resolution shortens the path; it cannot remove the round trip.

Operational note

The loopback device is a host kernel module and is not persistent across reboot. It must be loaded before the control plane starts, because device presence is detected at startup. Where it is absent, sessions run microphone-only and the camera is silently unavailable — worth an explicit health check in production.

06 — Transport

Getting media across a hostile network

WebRTC prefers UDP. Enterprise and public networks frequently do not permit it. The platform therefore ships three transport paths and negotiates whichever the client can actually use — this is the difference between working everywhere and demoing well.

Read this honestly. A reliable, ordered transport cannot discard a late packet, so a delayed frame holds up everything behind it — including audio, which shares the connection. On a UDP-blocked path with 45 ms of round-trip time, roughly 90 ms of interaction feedback delay is arithmetic, not a defect. Opening a single inbound UDP port improves interactivity more than any encoder setting available.
07 — Security model

Independent layers, each assuming the others failed

No single control is load-bearing. The design question for each layer is what it still prevents once everything above it has been defeated.

Layer What it enforces Holds even if… Status here
Execution boundary Page code runs in the container. The endpoint receives video and audio frames only. …the site is actively malicious and entirely unknown to any signature. Verified
Single-use container Fresh filesystem and profile per session; deleted on disconnect. …a site achieves persistence — it is discarded with the container. Verified
Browser policy lock Managed policy denies all URLs except the session's destination. Dev tools, downloads, sync and popups off. …the user tries to navigate elsewhere inside the stream. Site-dependent
Network isolation The container has no usable route of its own; the web is reachable only through the filtering proxy. …code ignores the browser proxy setting entirely. Not enforced
Egress allowlist The proxy permits only hosts belonging to active sessions, and filters content in transit. …a session attempts to reach an unrelated destination. Demo mode
In-container firewall Default-deny egress inside the container; only the proxy, DNS and media ports permitted. …a process bypasses every browser-level control. Not enforced
Container hardening Privilege escalation disabled; auto-removal on exit; per-session memory ceiling. …a container process attempts to gain privileges. Partial
Deployment status is stated separately from design on purpose, and this environment is a demonstration profile — not a hardened one. Measured directly, inside a live session:
  • Container egress is open. DNS resolves, an outbound HTTPS request to a public site returns 200, and a request to a raw IP address also succeeds. The container is on an ordinary bridge network with a default gateway, not the isolated network the design calls for.
  • The in-container firewall is absent. The packet-filter ruleset inside the container is empty.
  • The URL lock is site-dependent. It is enforced for single-domain destinations — a Wikipedia session carries a deny-all rule with a 23-entry exception list. It is deliberately lifted for the YouTube and Teams host families, because those applications span many domains and a single-host rule breaks video playback and sign-in.
What does hold, and was confirmed: page code executes only in the container and the endpoint receives video and audio; each session gets a fresh container that is removed on exit. Those are the load-bearing guarantees. The rest are configuration flags away from active, and should be switched on before any production claim rests on them.

09 — Workload validation

What has been exercised, and what has not

Isolation is easy to demonstrate on a static page and hard on a real application. All five workloads below were exercised on this deployment, including a live Teams call with camera and microphone — the hardest case, because it combines federated sign-in, conferencing and two-way media in one session.

The Teams case is worth understanding, because it generalises. Any application whose sign-in spans multiple domains conflicts with a one-destination lock. Supporting it means widening a session's allowlist to that application's identity and content domains — which is a deliberate, narrower guarantee than single-host isolation, and should be described that way rather than presented as equivalent. The change is understood and scoped; it is a policy decision as much as an engineering one.

Where the remaining effort is. The streaming platform works and is efficient: four workloads render, video and audio play, the client's camera reaches the isolated browser, sessions start in nine to sixteen seconds, and a video session costs well under one core. Roughly seven to eight concurrent sessions fit on this modest host.

The gap to a production claim is containment, and it is five specific items: move sessions onto the isolated network so the container has no route of its own; enable the egress allowlist and the in-container firewall; tighten capabilities to drop-all-then-add-back; stop spawning sessions for sub-resource requests, which both multiplies containers and lets a stray request claim a camera node; and resolve the multi-domain question so YouTube and Teams do not require lifting the URL lock wholesale. None is speculative and none blocks the others. Until they are done this is a strong demonstration of the isolation architecture rather than an enforced isolation boundary — a distinction worth stating plainly to customers, because the streaming half is genuinely ready and the containment half is not yet switched on.
